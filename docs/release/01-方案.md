# 发布流程（版本 + Changelog + 类型门禁 + npm 发布 + Release）

> **一句话**：在**仓库根目录**执行 `npm run release`，一条命令串起「类型门禁 → 选版本 →
> 写 Changelog → 提交打 tag → 推送」；推送 tag 即触发 GitHub Actions 完成 `npm publish` 与建 Release。
> **本机永不执行 `npm publish`**，**部署也不在其中**。

## 1. 前置

**发布前请先 `npm install` / `npm run setup`**（会自动 `prepare → husky` 安装 Git 钩子）。

## 2. 八个阶段

| 阶段 | 做什么 | 触发 / 执行 |
|------|--------|-------------|
| ① 类型门禁 | `npm run typecheck`（= `worker` + `web` 的 `tsc --noEmit` / `vue-tsc --noEmit`） | release 脚本自动跑，失败即中止 |
| ② 未提交检测 | `git status --porcelain`，有改动先让你填提交信息并二次确认 | release 脚本交互 |
| ③ 选版本 | ↑/↓ 选 patch / minor / major，只显示「当前版本 + 三档新版本号」 | release 脚本交互 |
| ④ 版本 + Changelog | `changelogen --<type> --bump` 写版本号 + 增量中文 `CHANGELOG.md` | release 脚本 |
| ⑤ 版本同步 | 把新版本号同步进 `worker/`、`web/` 的 `package.json`，避免漂移 | release 脚本 |
| ⑥ Release 说明预览 | 与 CI 同一个脚本，为空当场告警（否则 CI 会安静地建出空 Release） | release 脚本 |
| ⑦ 提交 + 打 tag + 推送 | `chore(release): vX.Y.Z` 提交、`git tag vX.Y.Z`、`push` + `push --tags` | release 脚本 |
| ⑧ npm 发布 + 建 Release | 版本一致性校验 → 离线自测 → 打包体检（`verify:pack`）→ `npm publish --provenance` → GitHub Release | **GitHub Actions**（tag 触发，`.github/workflows/release.yml`） |

## 3. 三条硬规则（别再退回）

| 规则 | 原因 |
|------|------|
| **本机永不 `npm publish`** | 发布只在 CI 做；需要仓库 Secret `NPM_TOKEN`，且必须是 **Automation** 类型（Publish 类型会因 2FA 失败） |
| **部署不在 `release` 里**（`npm run deploy` 单独执行） | tag 推上去就不可回滚，而部署失败发生在其后 → 会留下「版本已发布、站点还是旧的」中间态。理由见 [`../npm-publish/02-计划.md`](../npm-publish/02-计划.md) §5。**不要再把 `deploy` 加回 `scripts/release.mjs`** |
| **`npx` 使用时不 pin 版本** | 定时任务一律 `npx candidate-pool`，跟随 latest；阈值 / 权重随版本漂移是明确接受的取舍。**不要再建议 pin 版本** |

## 4. 门禁来自哪里

约定式提交（commitlint）通过 husky 的 `commit-msg` 钩子对**所有提交**强制校验——包括上面的 ② 与 ⑦，
不符合 `feat/fix/...` 规范会被拒绝。类型门禁通过 `pre-commit` 钩子执行
（仅当三个包的 `node_modules` 都已安装时，否则跳过并提示）。

> ⚠️ **本机 husky 跑不起来**（钩子进程 PATH 取自系统环境变量，没有 `sh`）。
> 变通：`.git/cph/` 下放等价钩子，提交时带 `-c core.hooksPath=.git/cph`。
> **门禁内容与原 husky 等价，绝不使用 `--no-verify`。**

## 5. 常用命令

```bash
# 日常：本地提交会自动过 commitlint + typecheck 钩子
git commit -m "feat(api): 新增 N2/N7/N9 涨幅口径"

# 发布（交互式选版本 → changelog → 打 tag → CI 发布 npm 与 GitHub Release）
npm run release

# 只预览 Release 说明（不发布任何东西）
npm run release:notes -- --tag v1.2.0
npm run release:notes -- --tag v1.2.0 --source git   # 强制走 git 兜底分支，便于比对

# 打包体检：敏感文件 / 运行数据守门 + 必需文件点名 + 代码覆盖 + 2MB 红线
npm run verify:pack
```

> `scripts/release-notes.mjs`：CHANGELOG 本版本段落优先，取不到回退 `git log` 分组。
> **别改用 `gh release create --generate-notes`**（只列有 PR 的变更，会漏掉直接提交的改动）。

### 5.1 `files` 白名单与 `verify:pack` 的四道闸

`package.json` 的 `files` 是**硬白名单**：目录级条目（如 `"eod/"`）会**绕过 `.gitignore`**，
把本地 20MB 级的 K 线缓存、逐日归档一并打进 tarball。2026-11-11 定位到一次真实事故：

| 版本 | `eod/data/` 布局 | `"!eod/data/eod-*.json"` | 发版结果 |
|------|------------------|--------------------------|----------|
| v3.2.0 | 95 个文件全在根层 | 匹配，有效 | 发布成功（线上最新 3.2.0） |
| v3.3.0 起 | 按管道搬进 `eod/`、`preopen/`、`pattern/`、`hotmoney/` 子目录 | **路径失配，静默失效** | v3.3.0 ~ v3.6.0 全被 2MB 红线拦下 |

故白名单已收窄成**显式 glob**：`eod/*.js`、`eod/*.json`、`eod/lib/*.{js,json}`、
`eod/data/industry-map.json`（唯一必需种子）、`db/*.{js,sql}`、`db/.env.example`。
`verify:pack` 对应四道闸：

1. **禁止入包**：凭据 / 本地库 / 日志 / `node_modules` / **整个 `eod/data/`（种子除外）**；
2. **必需文件**：点名 13 项，缺一即失败；
3. **代码覆盖**：用 `git ls-files bin eod db` 反查代码资产是否全部入包，防白名单收窄后漏文件；
4. **体积红线**：解包 > 2MB 即失败，并按二级目录打印 TOP 体积便于定位。

守门规则本身有正反例自检（14 正 / 8 反），防止后人顺手放宽正则。

> 新增 `eod/` 下代码文件时，若扩展名不是 `.js` / `.json`，记得同时补 `files` 白名单，
> 否则第 3 道闸会在 CI 直接拦下发版。

## 6. 版本号

版本号以根 `package.json` 的 `version` 为准，后续每次发布在此基础上递增；`worker` / `web` 与之保持同步。
