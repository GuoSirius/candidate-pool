# 发布流程（版本 + Changelog + 类型门禁 + npm 发布 + Release）

> **一句话**：在**仓库根目录**执行 `npm run release`，一条命令串起「类型门禁 → 选版本 →
> 写 Changelog → 提交打 tag → 推送」；推送 tag 即触发 GitHub Actions 完成 `npm publish` 与建 Release。
> **本机永不执行 `npm publish`**，**部署也不在其中**。

## 1. 前置

**发布前请先 `npm install` / `npm run setup`**（会自动 `prepare → husky` 安装 Git 钩子）。

## 2. 八个阶段

| 阶段 | 做什么 | 触发 / 执行 |
|------|--------|-------------|
| ① 类型门禁 | `npm run typecheck`（= `worker` + `web` 的 `tsc --noEmit` / `vue-tsc --noEmit`） | release 脚本自动跑，失败即中止 |
| ② 未提交检测 | `git status --porcelain`，有改动先让你填提交信息并二次确认 | release 脚本交互 |
| ③ 选版本 | ↑/↓ 选 patch / minor / major，只显示「当前版本 + 三档新版本号」 | release 脚本交互 |
| ④ 版本 + Changelog | `changelogen --<type> --bump` 写版本号 + 增量中文 `CHANGELOG.md` | release 脚本 |
| ⑤ 版本同步 | 把新版本号同步进 `worker/`、`web/` 的 `package.json`，避免漂移 | release 脚本 |
| ⑥ Release 说明预览 | 与 CI 同一个脚本，为空当场告警（否则 CI 会安静地建出空 Release） | release 脚本 |
| ⑦ 提交 + 打 tag + 推送 | `chore(release): vX.Y.Z` 提交、`git tag vX.Y.Z`、`push` + `push --tags` | release 脚本 |
| ⑧ npm 发布 + 建 Release | 版本一致性校验 → 类型门禁 → 离线自测（含规则引擎 22 项） → 打包体检（`verify:pack`）→ `npm publish --provenance` → GitHub Release | **GitHub Actions**（tag 触发，`.github/workflows/release.yml`） |

## 3. 三条硬规则（别再退回）

| 规则 | 原因 |
|------|------|
| **本机永不 `npm publish`** | 发布只在 CI 做；需要仓库 Secret `NPM_TOKEN`，且必须是 **Automation** 类型（Publish 类型会因 2FA 失败） |
| **部署不在 `release` 里**（`npm run deploy` 单独执行） | tag 推上去就不可回滚，而部署失败发生在其后 → 会留下「版本已发布、站点还是旧的」中间态。理由见 [`../npm-publish/02-计划.md`](../npm-publish/02-计划.md) §5。**不要再把 `deploy` 加回 `scripts/release.mjs`** |
| **`npx` 使用时不 pin 版本** | 定时任务一律 `npx candidate-pool`，跟随 latest；阈值 / 权重随版本漂移是明确接受的取舍。**不要再建议 pin 版本** |

## 4. 门禁来自哪里

约定式提交（commitlint）通过 husky 的 `commit-msg` 钩子对**所有提交**强制校验——包括上面的 ② 与 ⑦，
不符合 `feat/fix/...` 规范会被拒绝。类型门禁通过 `pre-commit` 钩子执行
（仅当三个包的 `node_modules` 都已安装时，否则跳过并提示）。

> ⚠️ **本机 husky 跑不起来**（钩子进程 PATH 取自系统环境变量，没有 `sh`）。
> 变通：`.git/cph/` 下放等价钩子，提交时带 `-c core.hooksPath=.git/cph`。
> **门禁内容与原 husky 等价，绝不使用 `--no-verify`。**

**CI 侧**（`.github/workflows/release.yml`）在 `npm publish` **之前**依次跑：
tag / `package.json` 版本一致性 → `npm run typecheck`（先 `npm ci --prefix worker|web`）→
`npm run selftest` → `npm run verify:pack`。本机漏跑任何一道，CI 都会拦下。
2026-11-11 审计补齐了「CI 比本机少一道 typecheck」和「规则引擎单测从未进 CI」两处不一致。

> **发布与 Release 是耦合的**：`npm publish` 排在「建 GitHub Release」之前，publish 失败会中断整条 job，
> Release 也不会创建。这正是 v3.3.0 ~ v3.6.0 只有 tag、没有 Release 的原因。
> 补齐请用 `backfill-releases.yml`（见 §8），**不要**为了建 Release 去重跑旧 tag 的发布流程
> —— 旧 tag 代码带着坏的 `files` 配置，重跑只会被再次拦下。

## 5. 常用命令

```bash
# 日常：本地提交会自动过 commitlint + typecheck 钩子
git commit -m "feat(api): 新增 N2/N7/N9 涨幅口径"

# 发布（交互式选版本 → changelog → 打 tag → CI 发布 npm 与 GitHub Release）
npm run release

# 只预览 Release 说明（不发布任何东西）
npm run release:notes -- --tag v1.2.0
npm run release:notes -- --tag v1.2.0 --source git   # 强制走 git 兜底分支，便于比对

# 打包体检：敏感文件 / 文件集合 / 必需文件 / 代码覆盖 / require 闭包 / 体积
npm run verify:pack
```

> `scripts/release-notes.mjs`：CHANGELOG 本版本段落优先，取不到回退 `git log` 分组。
> **别改用 `gh release create --generate-notes`**（只列有 PR 的变更，会漏掉直接提交的改动）。

### 5.1 `files` 白名单与 `verify:pack` 的六道闸

`package.json` 的 `files` 是**硬白名单**：目录级条目（如 `"eod/"`）会**绕过 `.gitignore`**，
把本地 20MB 级的 K 线缓存、逐日归档一并打进 tarball。2026-11-11 定位到一次真实事故：

| 版本 | `eod/data/` 布局 | `"!eod/data/eod-*.json"` | 发版结果 |
|------|------------------|--------------------------|----------|
| v3.2.0 | 95 个文件全在根层 | 匹配，有效 | 发布成功（线上最新 3.2.0） |
| v3.3.0 起 | 按管道搬进 `eod/`、`preopen/`、`pattern/`、`hotmoney/` 子目录 | **路径失配，静默失效** | v3.3.0 ~ v3.6.0 全被 2MB 红线拦下 |

故白名单已收窄成**显式 glob**：根层 `rules.js` 等点名文件、`eod/*.{js,json}`、`eod/lib/*.{js,json}`、
`eod/data/industry-map.json`（唯一必需种子）、`pulse/*.{js,mjs}` + `pulse/{lib,sources}/*.js`、
`db/*.{js,sql}`、`db/.env.example`；`CHANGELOG.md` 也移出了包体（唯一随发版次数单调增长、运行时完全不读的文件）。
`verify:pack` 对应六道闸：

1. **禁止入包**：凭据 / 本地库 / 日志 / `node_modules` / **`eod/data/`（种子除外）与 `pulse/{data,reports}/`**；
2. **文件集合登记**（`ALLOWED`）：包内每个文件都必须属于代码 / 模板 / 种子 / 元数据四类，
   未登记即失败 —— **体积只是结果，文件集合才是根因**。即使有人把 `files` 改回目录级 `"eod/"`，
   带进来的数据也会被逐文件拦下，不用等体积涨到 2MB；
3. **必需文件**：点名 16 项，缺一即失败；
4. **代码覆盖**：用 `git ls-files bin eod db pulse` 反查代码资产是否全部入包；
5. **运行时依赖闭包**：逐文件解析入包 JS 的 `require` / `import` 相对路径，指向包外即失败
   （先剥掉 JSDoc / 行注释，避免 `eod/lib/runlog.js` 里示例 `require` 的假阳性；`[^:]` 保护 URL 的 `https://`）；
6. **体积红线 + 单文件上限**：解包 > 2MB 或单文件 > 512KB 即失败，并按分类 / 目录打印 TOP。

每次体检都会打印**分类体积构成**（种子 / eod/lib / eod 根层 / pulse / db / 文档模板）与红线余量，
「代码正常增长」与「误打包数据」一眼可分；超过红线 80% 会提前提示，不再突然失败。
守门规则本身有正反例自检（禁入 16/10、集合 18/9、注释剥离），防止后人顺手放宽正则。

> **2026-11-11 二次核对抓到的真实断裂**：`files` 曾漏掉 `rules.js`（被 `gen_candidates.js` 等 8 个入包文件依赖，
> 装包后主命令直接 `Cannot find module './rules'`）与整个 `pulse/`（`npm run pulse` 和 `eod/rerender_all.js` 都依赖）。
> 点名清单永远抓不到间接依赖，故补上第 5 道闸。反向验证：临时移除二者 → EXIT 1、11 条依赖断裂 + 16 条资产遗漏被拦。

> 新增任何目录下的代码文件，记得同时补 `files` 白名单和 `ALLOWED`；
> 漏了会由第 4 / 5 道闸在 CI 直接拦下发版。

**`files` 精确核对结果（2026-11-11）**

| 检查项 | 结果 |
|---|---|
| 多余规则 | **无**：22 条规则每条至少命中 1 个文件，没有空规则 |
| 包内未被 `files` 解释的文件 | 仅 `package.json`（npm 强制包含；`README.md` 同样无法排除，故显式列出） |
| 运行时相对 `require` 闭包 | **完整**：105 个入包文件中所有 JS/MJS 的相对依赖都能在包内解析 |
| 有意排除 | `candidates.json`（用户观察池）、`rules.test.js`（不进 npm 包，但**已纳入** `npm run rules:selftest` / `npm run selftest`）、`pulse/{data,reports}/`、`eod/{data,reports}/`、`eod/logs/`、`CHANGELOG.md`、`db/migrations/`（按需目录，当前不存在） |
| 包体 | 105 文件 / 解包 1372.9 KB / 压缩 425.2 KB，距红线余量 675.1 KB |

### 5.2 「以后还会因为包体积变大而失败吗？」

| 增长来源 | 现在还会不会撑大 npm 包 |
|---|---|
| 逐日报告 / 原始快照 / K 线缓存 / perf 归档 | **不会**：`files` 精确 glob 不含 `eod/data/**`，且禁入规则与 `ALLOWED` 双重拦截，数据再多也进不了包 |
| `CHANGELOG.md`（每次发版追加） | **不会**：已移出白名单 |
| `industry-map.json` 种子 | 会，但极慢（v3.0.0 → v3.6.0 一直是 426.5KB）；超 512KB 会被单文件上限拦下 |
| 代码资产（新增模块、报告渲染器） | 会，属正常增长：v3.2.0 366KB → v3.6.0 712KB。**2MB 是人为兜底值，不是永恒常量** |

结论：这次的**数据累积型失败已结构性根除**；剩下唯一可能触线的是代码自身增长，
届时体检会打印出「全是代码资产」的构成，人工复核后调整 `SIZE_LIMIT` 并留痕即可，
**不要靠调大红线掩盖误打包**。

## 8. 发布 / 部署链路审计与 Release 补发（2026-11-11）

### 8.1 全链路逐环节核对

| 环节 | 触发 | 门禁 / 保护 | 核对结果 |
|---|---|---|---|
| 本机 `npm run release` | 手动 | 类型门禁 → 未提交检测 → 选版本 → changelog → 同步子包 → 说明预览 → commit + tag + push | 交互部分依赖 raw mode，非交互环境会退出；等效序列见 §8.3 |
| `.github/workflows/release.yml` | tag `v*.*.*` push | 版本一致性 → typecheck → selftest → verify:pack → publish → Release | **已补齐 typecheck**：此前 CI 比本机少一道 |
| `npm run selftest` | 本机 / CI | 12 项离线自测 | **已补 `rules:selftest`**：规则引擎 `node --test` 22 项此前从未进 CI |
| `scripts/verify-pack.mjs` | publish 前 | 六道闸（见 §5.1） | 已含文件集合登记与运行时 require 闭包 |
| `.github/workflows/deploy-archive.yml` | 工作日 19:30 / 21:05 / push `web/**` | `npm ci --prefix web\|worker` → 归档只读扫描 → 幂等指纹 → 凭据检查 → `npm run deploy` | 健全；与发版链路无共享资源，可并发 |
| `web/scripts/deploy.mjs` | 被上一步调用 | 同源模式检查 / `wrangler.toml` 存在性 / 构建 / `wrangler pages deploy` | 健全 |
| `daily-screen` / `tail-screen` / `tail-observe` | 定时 / 手动 | 产物提交到 `daily-artifacts` 分支 | 与 `main` 隔离，不触发发版或部署 |
| `refresh-industry-map.yml` | 每月 1 日 / 手动 | 双源抓取 + 自洽闸 + 防降级闸，提交到 `main` | 只改 `eod/data/industry-map.json`，不命中 `web/**`、不是 tag → 不会误触发部署或发版 |

**结论**：「目录级白名单 + 排除规则失配 + 只看总量」这一根因已由 §5.1 六道闸结构性根除；
本轮进一步补齐「CI 门禁少于本机」「核心单测不进 CI」两处同类隐患，并把 Release 补发做成幂等工具。

### 8.2 补发历史 Release

`v3.3.0` ~ `v3.6.0` 四个 tag 都在远端，但当年 `verify:pack` 失败 → `npm publish` 未执行 →
「建 GitHub Release」步骤没跑到；npm 上同样**没有**这些版本号（线上 `3.2.0 → 3.6.1`）。
所以只补 Release，**不重跑 publish、不改 tag**。

`.github/workflows/backfill-releases.yml`：

- `workflow_dispatch` 可指定 `tags`（默认那 4 个）与 `dry_run`；首次加入时由 `push.paths` 自动跑一次；
- 每个 tag 先 `gh release view`，已存在即跳过（幂等）；tag 不存在直接报错中止，不静默漏发；
- 说明由 `scripts/release-notes.mjs --tag <tag> --unpublished --install` 生成：从 `CHANGELOG.md` 取本版本段落，
  顶部加「npm 上不存在该版本号」警示，安装命令指向 `latest`；
- `--verify-tag` 确保只给已存在的 tag 建 Release；`--latest=false` 防止历史版本抢走 Latest，
  末尾再兜底把最高版本 tag 设回 Latest。

### 8.3 非交互等效发版序列（AI / 脚本代跑用）

`npm run release` 的 `selectRelease()` 依赖 `stdin.setRawMode`，非交互环境直接退出。等效序列：

```bash
npm run typecheck
node node_modules/changelogen/dist/cli.mjs --patch --bump       # 写版本号 + CHANGELOG
# 同步 worker/package.json、web/package.json 的 version
node scripts/release-notes.mjs --tag vX.Y.Z --install           # 说明预览，必须非空
npm run verify:pack && npm run selftest
git add package.json worker/package.json web/package.json CHANGELOG.md
git commit -m "chore(release): vX.Y.Z" && git tag vX.Y.Z
git push origin <SHA>:refs/heads/main
git push origin refs/tags/vX.Y.Z:refs/tags/vX.Y.Z
```

> 自查发布结果时 `npm view` 要加 `--prefer-online --registry=https://registry.npmjs.org`：
> 本机默认走 `registry.npmmirror.com` 且吃缓存，发布成功后仍可能读到旧版本。
