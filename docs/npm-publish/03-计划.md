# 独立发布 · 实施计划（方案 A：全量打包 + GitHub 自动发布）

> **一句话**：本机只负责 `bump 版本 → 写 CHANGELOG → 提交 → 打 tag → push`，`npm publish` 与 GitHub Release **全部在 CI 完成**；发布前必过「版本一致 / 离线自测 / 打包体检」三道闸。
>
> 前置方案对比见 [02-方案.md](02-方案.md)（三方案取舍与边界清单）。

## 1. 已定策略

| 决策 | 结论 | 依据 |
|------|------|------|
| 打包范围 | **方案 A：全量打包**（根 + `eod/` + `db/`） | 尾盘脚本跨目录依赖仓库根（`../notify`、`../../db/*`），「只发尾盘」要把依赖内收 → 结构分叉，代价大于收益 |
| 发布执行者 | **GitHub Actions**，由 tag 推送触发 | 与 `yyds` / `change-image-suffix` / `uuid-nanoid` / `enhance-axios` 一致；本机不必持有 npm 凭据（`yyds` 里那句注释就是这个意思：*Publishing happens here (CI), not in the local `npm run release`*） |
| Release 说明 | `CHANGELOG.md` 本版本段落，**取不到则用 `git log` 兜底** | 满足「每个版本的所有提交变化都可见」；自动 notes 只列有 PR 的变更，本仓库直接推 main → 会只剩一行 compare 链接 |
| 包名 | `candidate-pool`（公开包） | `npm view` 实测未占用；仓库本身已公开，发 npm 不新增暴露面 |
| 包入口 | `bin/` 两个转发入口，默认工作目录 = **当前目录** | `paths.js` 的默认 HOME 是包根（为保持仓库内运行行为不变），装包后必须改指 cwd，否则产物写进 `node_modules` |
| **部署** | **移出 `release`，与发版解耦** | 见 §5 |
| **版本 pin** | **定时任务不 pin，直接用 `npx candidate-pool`** | 见 §7 |

## 3. 首次运行脚手架（Phase 1，已完成）

空目录（`npx` / 装成依赖）首跑原本会**直接报错**（缺 `candidates.json`）；现在两个入口在任何实质动作之前都会做一次幂等补齐。

### 3.1 补什么

| 补齐项 | 来源 | 说明 |
|--------|------|------|
| `data/`、`reports/`、`eod/data/`、`eod/reports/`、`db/` | `mkdir -p` | 产物目录，缺了会在写入时才报错 |
| `candidates.json` | 包内 `candidates.example.json` | **唯一硬阻塞项**：缺它 `gen_candidates.js` 直接抛错。生成后带 `note` 说明「这是示例模板，请用 `node build_universe.js` 重建」 |
| `eod/data/industry-map.json` | **不复制** —— `eod/lib/sector.js` 直接回退读包内那份 | 它是由工作流生成的**派生缓存**（一年变几次），不当用户资产；读了才不至于全市场塌成单一「未分类」 |

### 3.2 **不**补什么（只打印 `cp` 命令提示）

| 文件 | 模板 | 为什么不自动创建 |
|------|------|------------------|
| `notify_config.json` | `notify_config.example.json` | 一旦写入占位值，程序会从「未配置 → 跳过」变成「配了假值 → **真的去发**」，行为静默改变 |
| `db/.env` | `db/.env.example` | 同理，占位凭据会让 D1 客户端以为有凭据，报出误导性的网络错误 |

### 3.3 触发时机与输出

```
npx candidate-pool                    # 静默补齐后继续正常运行（什么也不缺时零输出）
npx candidate-pool --init             # 只做初始化然后退出 + 打印可选配置的 cp 命令
npx candidate-pool --paths            # 纯诊断，不触发脚手架（不产生任何写入）
```

`--init` 与「静默补齐」是两个不同的入口：前者是你主动想确认环境，所以**无论有没有变化都给你回音**；
后者是日常流程的一部分，**只在实际创建了东西时出声**。

> 首次运行时这条补齐是**必须**的：`npm run selftest` 已把脚手架自测纳进去（见 §9）。

## 4. 发布链路

```
本机  npm run release                      ← 只有这一条命令，跑完即「发布已启动」
      ├─ 类型门禁 → 未提交检测 → 选 patch/minor/major
      ├─ changelogen --bump（改 package.json 版本 + 增量写 CHANGELOG.md）
      ├─ 同步 worker/web 子包版本
      ├─ **打印 Release 说明预览**（与 CI 同一个脚本，所见即所得；为空则当场告警）
      ├─ 提交 chore(release): vX.Y.Z → git tag vX.Y.Z → push 分支与 tag
      └─ 打印三条链接：Actions 运行日志 / npm 包页 / Release 页
              ↓ tag 推送触发（无需本机再做任何事）
CI    .github/workflows/release.yml
      ├─ ① 校验 tag 与 package.json 版本一致
      ├─ ② npm ci
      ├─ ③ npm run selftest（离线：路径 42 + 脚手架 36 + 时段 66 + 结构同步 19 = 163 项）
      ├─ ④ npm run verify:pack（打包体检）
      ├─ ⑤ npm publish --provenance --access public
      ├─ ⑥ 生成 Release 说明 → softprops/action-gh-release@v2
      └─ ⑦ 往 Actions 摘要写「包名 / 版本 / npm 链接 / Release 链接」
```

**本机永不执行 `npm publish`**；本机命令的职责就是「把 tag 推上去并告诉你去哪看结果」，因此它会把
Actions / npm / Release 三条链接直接打出来（约 1~2 分钟出结果，标红最常见原因是没配 `NPM_TOKEN`）。

### `npm run release` 与 `npm run release:notes` 的区别

| 命令 | 做什么 | 会发布吗 |
|------|--------|----------|
| `npm run release` | 完整发版：bump + CHANGELOG + **说明预览** + 提交 + 打 tag + push | 会（**间接**：打 tag → CI 自动 publish 并建 Release） |
| `npm run release:notes` | 只**渲染**一段 Release 说明文本（CHANGELOG 段落优先，git 兜底） | **不会**，纯只读，不发任何请求 |

`release:notes` 就是 `release` 里那次预览的独立入口，用途：发版前单独核对措辞、事后排查
「Release 说明为空 / 少了提交」，或强制 `--source git` 与 CHANGELOG 版本比对。
它同时支持**「tag 尚未创建」的预览**（`--tag vX.Y.Z` 时若该 tag 不存在，自动按 `HEAD` 统计并提示）。

## 5. 部署已移出 `release`

`scripts/release.mjs` 末尾原来的 `npm run deploy --prefix worker` + `--prefix web` **已删除**。

理由（两条，任一都足够）：

1. **tag 一旦推上去就不可回滚，而部署失败发生在那之后** —— 结果是「版本已发布、站点还是旧的」的中间态，很容易被误判成「发布失败」并让人去重试发版。
2. **网页的静态资源与 API 现在由同一个 Pages 项目承载**（独立 Worker 已退出发布流程），发不发版都可能需要单独部署；把它绑死在 `release` 里，等于给一个纯版本动作附上副作用。

需要上线时单独执行：

```bash
npm run deploy        # = npm run deploy --prefix ./web（静态资源 + /api 一起）
```

## 6. 向后兼容（四条保票）

发 npm 包**不得改变已经在跑的用法**。仓库内直接跑脚本、本地 WorkBuddy 定时任务、GitHub Actions 三条既有路径都必须逐字节不受影响。

| # | 保票 | 由谁保证 | 怎么验 |
|---|------|----------|--------|
| 1 | **仓库模式行为完全不变** —— 默认工作目录仍是包根（= 历史 `__dirname`） | `paths.js` 的解析优先级里，`pkg-root` 是兜底；只有 `bin/` 入口会改指 cwd | `paths.selftest.js` 里专门有一节钉死「默认值必须等于历史 `__dirname`」——这条被改错会导致本机/CI **静默换目录**（不报错，只是文件不见了） |
| 2 | **已有文件一个字节都不改** | `scaffold.js` 只创建**缺失**的目录与文件，`existsSync` 命中即跳过 | `scaffold.selftest.js` `[3]`：预置一份自定义 `candidates.json` + `notify_config.json`，跑完后逐字节比对未被改写 |
| 3 | **不写占位凭据** | 脚手架对 `notify_config.json` / `db/.env` 只提示、不创建 | `scaffold.selftest.js` `[2]`：断言这两个文件在空目录里**不存在** |
| 4 | **快照 / 归档格式不变** | 本轮未动 `data/snapshot-*.json`、`eod/data/eod-*.json` 的结构与命名 | `eod/lib/trading.selftest.js` 60 项 + 尾盘 `--replay` 回放实测 |

另外两条相关约定：

- 脚手架**幂等**（连跑三次零副作用），且任何内部错误只降级为一行警告、**不阻断主流程** —— 首跑失败不该把「今天没数据」变成「程序崩了」。
- 当工作目录落在 `node_modules` 里（说明是被当依赖安装且用户没给 `--cwd`）时，脚手架会额外打印一段重定位警告，指出产物会随重装 / npx 清缓存一起丢失。

## 7. `npx` 使用时不 pin 版本（已定）

定时任务与临时使用一律 `npx candidate-pool`（跟随 latest），**不写 `@1.2.0` 这类固定版本**。

- 收益：阈值调整、口径修正、bug 修复**发布即生效**，不必逐个改定时任务与文档。
- 代价：`eod/tail.config.js` 里的阈值与 `screen.js` 的评分口径会随新版本变化 —— 这是明确接受的取舍。
- 已知会这样变的地方（新版本上线即生效）：`filter.*`（涨幅/量比/换手/市值门槛）、`score.weights`（六项权重）、`session.*`（时点与盘中窗口）。
- 缓释手段（都已在位）：`CHANGELOG.md` 按提交类型分组记录每一次改动；`npm run release` 在打 tag 前打印说明预览；CI 发布前必过离线自测与打包体检；`eod/tail.config.js` 每个参数都写明「口径与调优方向」便于对照。

## 8. 踩过的坑（都已在代码里留注释）

| 坑 | 现象 | 修法 |
|----|------|------|
| `npm pack --json` 的形状 | 是**以包名为键的对象**，不是数组；按 `[...]` 截取会切进 `files` 数组 → `JSON.parse` 失败 | 直接解析，失败再退化为「首个 `{` 到末个 `}`」 |
| Windows 下 spawn `npm.cmd` | `spawnSync npm.cmd EINVAL` | `shell: true`（参数是常量，无注入面） |
| `changelogen` 的 `repo` | 配了 `{ provider, repo }`（**缺 `domain`**）→ 它跳过推断，拼出 **81 个** `https://undefined/...` 死链 | 删掉该键，交给 `package.json.repository` 推断；已用 `loadChangelogConfig()` 实测确认 `domain: github.com` |
| 首次发布没有上一版 tag | `git describe <tag>^` 失败并打脏 stderr | `git()` 支持 silent 模式，首次发布视为正常分支 |
| 自测泄漏临时目录 | `paths.selftest.js` / `scaffold.selftest.js` 每跑一次留 2 个目录 | 收尾清理，连跑两次残留为 0 |
| 脚手架「已就绪」被吞掉 | `--init` 时若只有「可选配置提示」而没有新建文件，会跳过「已就绪」那行 → 看起来像没跑 | `--init` 分支独立判断：无变化就打「已就绪」，与提示并排输出 |

## 10. 与既有项目的一致性

| 项 | 本项目 | `yyds` | `uuid-nanoid` | `enhance-axios` | `change-image-suffix` |
|----|--------|--------|---------------|-----------------|----------------------|

**本仓库额外补的三道闸**（其它项目没有）：版本一致性校验、离线自测、打包体检 + 守门规则自检。
值得回填到其它项目——`npm publish` 前跑一次白名单体检，是防凭据泄露成本最低的一步。
