# 独立发布（npm 包 / 免拉代码运行）· 方案对比

> **结论（2026-09-21）**：选定**方案 A：全量打包**，并采用「本机打 tag → GitHub Actions 执行 `npm publish` + 建 Release」。实施细节、验证清单与遗留项见 [03-计划.md](03-计划.md)。

> **一句话**：把「拉代码运行」变成「装包运行」，难点**不在发布动作本身**，而在**产物与配置的落点** —— 装进 `node_modules` 后代码必须能定位到用户的工作目录，否则写出来的文件会被下一次重装 / `npx` 清缓存吞掉。

## 1. 目标与不变量

**目标**：不拉代码即可运行两个入口 —— 次日候选池（`gen_candidates.js`）、尾盘选股（`eod/tail_screener.js`）。

**不变量**（无论最后选哪个方案，都不许破坏）：

| # | 不变量 | 原因 |
|---|--------|------|
| 1 | 默认仍是「拉代码运行」，行为**逐字节不变** | 本机 WorkBuddy 定时任务（3 个）与 GitHub Actions（4 个 workflow）都直接调仓库内脚本路径 |
| 2 | 数据 / 报告 / 配置的落点由用户控制，**绝不写进包目录** | 包目录会被重装覆盖；`npx` 缓存更是跑完即失 |
| 3 | 三条通道（本机 / CI / 装包）跑**同一份代码、同一套阈值** | 口径一旦分叉，N 周期复盘就不成立 |

## 2. 两种运行模式的本质区别

| 维度 | 拉代码（现状） | 装包 / npx |
|------|----------------|-----------|
| 代码位置 | 仓库目录，**可写** | `node_modules/<pkg>` 或 `~/.npm/_npx/...`，**不该写、会被清** |
| 路径锚点 | `__dirname` = 仓库根，**恰好等于**用户工作目录 | `__dirname` = 包目录，**与**用户工作目录**无关** |
| 配置来源 | 仓库内文件（`candidates.json` / `notify_config.json` / `db/.env`） | 无处可放 |
| 依赖 | 仓库 `node_modules` | 包自身依赖（很轻，见 §3） |
| 更新 | `git pull`（用户显式、可审阅） | `npm i -g` / `npx @latest` —— **可能静默升版** |
| 跨目录引用 | 可 `require` 仓库任意文件 | 只能引同包内文件 |

> 结论：**第 2 行是全部问题的根源**。其余各行都是它的衍生。

## 3. 现状核查（2026-09-21 实测）

| 项 | 事实 | 影响 |
|----|------|------|
| 工作区路径 | 根 + `eod/` + `db/` 共 **10 处**，原先全部锚在 `__dirname` | 装包后全部写错位置 → **已改造（§7）** |
| 尾盘跨目录依赖 | `eod/tail_screener.js` → `../notify`、`../../db/d1client`、`../../db/ddl`（+ `db/schema.sql`） | **不能只打包 `eod/`** |
| 包元数据 | `private: true`、`name: candidate-pool`、`version: 1.1.0` | 要发布须去 `private`；名称需先查是否被占（**未查**），建议 scoped |
| 生产依赖 | `dayjs` + `dotenv`，**无原生模块** | 安装成本极低，打包无编译负担 |
| 已有发布设施 | `changelogen` + `scripts/release.mjs` + commitlint | 版本与 changelog 流程已就绪，缺的只是 `npm publish` |
| 定时任务 | 本机 3 个 + Actions 4 个，均直接调**仓库内脚本路径** | 切到包运行需同步改，且必须 pin 版本 |

## 4. 边界情况清单

| # | 边界 | 拉代码 | 装包 | 对策 |
|---|------|--------|------|------|
| 1 | 快照 / 报告写哪 | 仓库内，天然正确 | 写进包目录 → 重装即丢 | 工作目录可重定位（§7） |
| 2 | 配置放哪 | 仓库根 | 无处可放 | 同上，`<HOME>/notify_config.json` |
| 3 | 行业映射缓存 | 仓库内，月更 CI 提交 main | 用户机器上没有该文件 | 首次运行需能自建（调 `build_industry_map.js`）或降级为「未分类」 |
| 4 | 观察池 `candidates.json` | 仓库内、用户已调好 | 不存在 | 需脚手架生成（`build_universe.js`）或从示例复制 |
| 5 | D1 凭据 | `db/.env` | 不存在 | 可选能力：不配就跳过落库（现有行为已是「缺凭据静默跳过」） |
| 6 | 本地 SQLite | `db/local.db` | 不存在 | 打开时自动应用 `db/schema.sql`（**代码资产**，随包走） |
| 7 | 定时任务升级风险 | `git pull` 可控 | `@latest` **静默换阈值** | 必须 pin 版本（§6 Phase 3） |
| 8 | 离线/回放快照格式 | 同仓库同版本 | 包升级可能改格式 | 快照格式需向后兼容，或加 `snapshotVersion` |
| 9 | 通知默认行为 | 有配置就推 | 新用户无配置 | 保持「未配置 → 只出报告不推」 |
| 10 | 时区 | 已统一 dayjs + `Asia/Shanghai` | 同 | 无需额外处理 |

## 5. 三个候选方案

### 方案 A：全量打包（一个包含候选池 + 尾盘 + db 工具）

| 项 | 内容 |
|----|------|
| 做法 | 一个包，`bin` 暴露 `candidate-pool`（候选池）与 `tail-screener`（尾盘）两个命令；工作目录由 `CANDIDATE_POOL_HOME` / `--cwd` 指定 |
| 改动量 | 依赖 §7 已完成；**剩余**：`bin/` 两个转发脚本、首次运行脚手架、README 用法章节 |
| 优点 | 与仓库结构 1:1，尾盘的跨目录依赖天然满足；一份代码两处用，口径不可能分叉 |
| 缺点 | 会把 `web/`、`worker/` 一起带进包（需 `files` 白名单排除）；包体积偏大 |

### 方案 B：只发尾盘

| 项 | 内容 |
|----|------|
| 做法 | 只把 `eod/` + `notify.js` + `db/{d1client,ddl,schema.sql}` 打成一个包 |
| 改动量 | 需要把尾盘对根目录的依赖**内收**（复制或提取共享模块），否则包不完整 |
| 优点 | 用户心智最清爽：尾盘是「独立工具」 |
| 缺点 | **与仓库结构分叉** —— 同一份逻辑要维护两处（或做构建期搬运），长期是隐患；候选池（用户最常跑的）反而仍要拉代码，收益最小 |

### 方案 C：不发 npm，走 `npx github:` / git submodule

| 项 | 内容 |
|----|------|
| 做法 | 使用者执行 `npx --yes github:GuoSirius/candidate-pool --offline`（或把仓库作为 submodule 引入） |
| 改动量 | 思路上看是「零发布」，但**仍然需要 §7** —— `npx github:` 会 clone 到 npm 缓存目录，`__dirname` 同样不等于用户工作目录，产物照样会写错地方 |
| 优点 | 不占用 npm 名称、不涉公开/私有决策、与仓库结构完全一致 |
| 缺点 | 安装体验不如 `npm i -g`；无法用 npm 的版本语义做 pin（需用 commit SHA 或 tag）；GitHub 不可达时不可用 |

### 对比总表

| 维度 | A 全量打包 | B 只发尾盘 | C npx github |
|------|-----------|-----------|--------------|
| 需要「可重定位」层 | 是 | 是 | **是** |
| 额外改动量 | 中（bin + 脚手架） | 中大（拆依赖，结构分叉） | 小 |
| 与现仓库结构一致性 | 高 | **低（分叉）** | 高 |
| 版本可 pin | 好（semver） | 好 | 一般（需 SHA/tag） |
| 安装体验 | 好 | 好 | 一般 |
| 需要公开决策 | 是 | 是 | 否 |
| 口径分叉风险 | 低 | **中高** | 低 |
| 结论 | 若确定要「装包运行」，选它 | 不推荐（收益最小、代价最大） | 想先试水、暂不公开时选它 |

> **关键结论**：三个方案**都必须先做「可重定位」**（§7，已完成）。方案 B 的额外代价（结构分叉）远大于它的收益，可以排除。A 与 C 的差别只在「发布方式」，代码侧完全相同。

## 6. 建议与落地顺序

| 阶段 | 内容 | 状态 |
|------|------|------|
| Phase 0 | **可重定位层**：`paths.js` + 10 处路径改造 + 自测 | **已完成（本轮）** |
| Phase 1 | 首次运行脚手架：目标目录为空时生成 `candidates.json`（`build_universe.js`）、`eod/data/industry-map.json`（`build_industry_map.js`）、`db/.env` 模板；并在文档写清用法 | 待定 |
| Phase 2 | 按选定方案落地：A → `bin/` + `files` 白名单 + 去 `private`；C → 写 `npx github:` 用法章节 | 待定 |
| Phase 3 | 定时任务切到 pin 版本（本机 3 个 + Actions 4 个），避免静默升版改口径 | 待定 |

> Phase 1 是 A / C **共同的**前提（新用户机器上一个文件都没有）；建议先做 Phase 1，再决定 Phase 2。

## 7. 已完成：可重定位层（`paths.js`）

**解析优先级**（一次解析后缓存）：`setHome()` > `CANDIDATE_POOL_HOME` > `--cwd <dir>` > **包根（默认，与历史行为逐字节一致）**

| 类别 | 路径 | 是否随工作目录移动 |
|------|------|--------------------|
| 工作区 | `candidates.json`、`data/`、`reports/`、`notify_config.json`、`eod/data/`、`eod/reports/`、`db/local.db`、`db/.env` | **是** |
| 代码资产 | `db/schema.sql`、`db/migrations/`、全部 `.js` | **否（永远跟包走）** |

- 自检命令：`npm run paths`（= `gen_candidates.js --paths`，尾盘侧为 `tail_screener.js --paths`）→ 打印实际解析结果与来源，专治「文件到底写到哪去了」。
- 回归自测：`npm run paths:selftest`（41 项，覆盖默认值必须等于历史 `__dirname`、两类重定向、优先级、`--cwd` 解析健壮性、代码资产不动）。
- 全量自测入口：`npm run selftest`（paths + tail + db）。
- 端到端实测：把快照与观察池复制到临时目录，`CANDIDATE_POOL_HOME=<临时目录>` 跑离线模式 → 报告落在 `<临时目录>/reports`，**原仓库文件数不变**。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 有人把默认 HOME 改成 `process.cwd()` | 本机/CI 静默换目录（不报错，只是文件不见了） | `paths.selftest` 第 [1] 节把默认值钉死 |
| 定时任务用 `@latest` | 阈值/口径被静默升级 | Phase 3 必须 pin 版本 |
| 包升级改快照格式 | 旧快照读不出 | 快照加版本字段或保持向后兼容 |
| 把 `web/`、`worker/` 打进包 | 体积膨胀、暴露无关代码 | `files` 白名单 |
| 公开包后误带凭据 | 泄露 | `npm pack` 后先看 `--dry-run` 列表；`notify_config.json` / `db/.env` 已在 `.gitignore`，仍需在 `files` 白名单层面排除 |

## 9. 待确认（需要你拍板）

1. **Phase 2 走 A 还是先 C？** 我倾向：先只做 Phase 1；若只是「换台电脑想直接用」，C 足够且无需公开决策。
2. **是否公开包？** 涉及交易策略，建议私有（私有 npm 或自建 registry），否则阈值全公开。
3. **是否需要 Phase 1 的脚手架**（自动生成观察池与行业映射）？不做的话，新用户机器上首跑会缺文件。
4. **名称**：`candidate-pool` 是否已被占用需实查；建议 `@<scope>/candidate-pool`。
