## 3. 与原设计的关键差异

| 原设计（本文引用的四篇文档） | 实际落地 | 差异原因 |
|------|----------|----------|
| **Q2** 建议放**独立新仓库**，便于独立调度与发布 | 落在 **`candidate-pool` 内**（`eod/` 目录） | 复用行情抓取、通知、D1、发布链路，省掉跨仓库耦合；调度也没混——尾盘有独立 workflow |
| **Q3** 建议「先落本地 JSON」，稳定后再决定是否同步 D1 | **直接落 D1**（`tail_run` / `tail_pick`），本地 JSON 仍作权威归档 | 网页端要展示；口径未稳时靠 `mode` 区分而不是靠「不落库」 |
| **Q4** 建议只「传 GitHub 仓库存档」 | 走 **`daily-artifacts` 分支**（与初筛产物同处），不上公网 | 与原建议方向一致，只是归属分支统一了 |
| **Q11** 展示总分 + 分项明细 | 实现为 **六维、分两组呈现**（个股自身 65 / 环境与质量 35） | 让「靠板块撑起来的高分」一眼可辨，避免误读 |
| **Q12** 每组最多 2–3 只 | 实现为**分组排序 + 组内最优标记 + 组内 x/y**，不做硬性截断 | 保留信息量，把去重决策交给人 |
| **Q13** 只 14:50 单点，先不做盘中多点 | 实为**三口径**：`cut`（正式）+ `observe`（14:30 起观察）+ `intraday`（随时手动） | 需要一个「盘中随手看一眼」的口径；但它**不落库不推送**，不会污染正式口径 |
| **Q14** 接受 Actions 只作备份，主通道放本地 | 维持该结论，且已被实测证实（§4） | Actions 延迟远超「数分钟到数十分钟」的预估 |
| 报告「传仓库存档」 | 与初筛产物一起进 `daily-artifacts` | — |

## 4. 已暴露的问题与结论

### 4.1 落库两处事故（2026-09-21，已修）

线上四个尾盘页面全 500 / 全空，根因都在**数据层**，与前端无关：

| 根因 | 结论（别再退回） |
|------|------------------|
| `tail_pick` 列清单 33 列却手写 32 个 `?` → 每条候选 `7500 32 values for 33 columns`；而 `d1client.batch()` 是分片 `Promise.all` **不是事务** → 「运行记录写进去了、候选一条没有」 | **占位符必须由列清单派生**，并写进自检（`tail:selftest` §10 逐列比对 `db/schema.sql`） |
| 本地把 14:50 固定口径叫 `cut`，D1 / API 只认 `formal` → 记录页把它兜底显示成「观察」 | 写入侧 `d1Mode()` 翻译；读取侧 `MODE_ALIAS` / `toTailMode()` 兼容；**别再让 `cut` 进 D1** |

另外 `tail_run` / `tail_pick` 曾经**两个库都没建**（同一份 DDL 散落三处、两条自动应用路径都坏），
现由 `db/schema.sql` 单一真相源 + `npm run db:migrate:both` 兜住。

### 4.2 GitHub Actions 的 `schedule` 实测延迟远超预期（2026-09-21 实测）

用户 16:29 反馈「三个定时任务都没执行」。查证结论：

- 5 个工作流状态**全部 `active`**，cron 值正确，仓库未 archived / disabled —— **配置没错**。
- **延迟是小时级**：cron 一直是 `35 7`（07:35 UTC = 15:35 北京）时，实际 `created_at` 长期落在
  **12:13–12:51 UTC（≈ +5 小时）**；8 月底一度 **+7~12 小时**。运行本身很快（created 与 updated 相差约 1 分钟），
  所以**是 GitHub 调度排队，不是任务慢**。
- 三个 schedule 在 09-20 / 09-21 两天内被新增或改动过，进一步降低当日触发概率。

**结论：尾盘（14:20 / 14:40 分钟级窗口）不能依赖 GitHub Actions 主跑。**
延迟 5 小时会直接越过「收盘后 120 分钟内可补跑」的窗口，被时段守卫拒绝。
**主通道是本地计划任务，Actions 只作备份** —— 与 Q14 的判断一致。

### 4.3 `daily-artifacts` 推送步骤曾失败（已修，待验证）
