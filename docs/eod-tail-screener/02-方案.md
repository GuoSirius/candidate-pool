# 尾盘选股 · 方案

> 📌 **状态：已实现并上线（2026-09-20 起）**。本文是**方案基线**，保留原始设计，**不回改**。
> 实现过程中的口径调整（六维打分分两组、观察/盘中两种额外口径、落 D1、文件名「一天一个」等）
> 见 [`05-复盘.md`](05-复盘.md)；**当前可用的口径速查以 [`../ops/01-方案.md`](../ops/01-方案.md) 为准**。

> **一句话**：复用 `candidate-pool` 已验证的「纯 Node 直连腾讯行情」链路，新增一套**尾盘口径**的过滤 + 打分 + 分组排序，输出报告并落库攒样本。

## 1. 数据链路

| 用途 | 接口 | 备注 |
|------|------|------|
| 全市场实时快照 | `https://qt.gtimg.cn/q=<code>,<code>,...` | 批量拉取；价格、涨幅、成交量额、换手、流通/总市值、涨跌停价均在同一响应内 |
| 近 5 日均量 / 前 10 日高点 | `https://web.ifzq.gtimg.cn/appstock/app/fqkline/get?param=<code>,day,,,260,qfq` | 多源回退：`ifzq.gtimg.cn`、`proxy.finance.qq.com`（沿用现有 `KLINE_SOURCES`） |
| 尾盘段分时 | 现有 `fetchMinute(code)` | 仅返回最新交易日；历史日按「数据缺口」处理 |
| 行业归类 / 板块强度 | 现有 `computeSectors()` 自算 | 不依赖外部板块接口 |
| 通知 | 现有 `notify.js` | Server酱 / PushPlus 微信 + 163 邮箱 |

> 以上全部走 Node 内建 `https`，**零第三方依赖、零 skill 依赖** —— 这是「本地与 GitHub 都能执行」的前提。

## 2. 筛选规则（初值，等确认）

| 项 | 门槛 | 理由 |
|----|------|------|
| 当日涨幅 | +2% ~ +7% | 太低无动能；太高接近涨停、买不到 |
| 量比（14:50 时点） | ≥ 1.2 | 当日量能相对近 5 日均量放大 |
| 换手率 | 2% ~ 20% | 过低无人气；过高警惕出货 |
| 流通市值 | 20 亿 ~ 500 亿 | 与现有口径保持一致，便于横向对照 |
| 尾盘段涨幅（14:30→14:50） | ≥ +0.5% | 尾盘走强的核心特征 |
| 现价 vs 当日均价 | 现价 ≥ 均价 | 站上均价线视为强势 |
| 距日内高点 | ≤ 1.5% | 未明显回落 |
| 排除项 | ST / 停牌 / 一字板 / 已封涨停 / 上市 < 20 个交易日 | 不可买或噪声过大 |

## 3. 强度打分（总分 100，分项可解释）

| 分项 | 权重 | 口径 |
|------|------|------|
| 尾盘动能 | 30 | 14:30→14:50 涨幅（线性映射，+2% 封顶） |
| 量能 | 20 | 量比（1.2→0 分，3.0→满分） |
| 位置 | 15 | 距日内高点越近越高 |
| 均价线强度 | 10 | 现价 ÷ 当日均价 的超出幅度 |
| 板块强度 | 15 | 所属行业当日涨幅的全市场分位 |
| 换手适中度 | 10 | 落在 3%–10% 得满分，向两端递减 |

输出每只票的**分项得分明细**，报告里直接展示，避免「黑箱打分」。

## 4. 同类比较与排序（FR-07）

| 步骤 | 做法 |
|------|------|
| 分组 | 按申万一级行业（自算）分组 |
| 组内排序 | 按总分降序 |
| 呈现 | 每组列前 3 只并标记「**组内最优**」；另设「全市场 TOP 10」区块 |
| 去重提示 | 同组内相关性过高的标的只保留前 1–2 只（避免推一堆同质票） |

## 5. 调度方案对比

| 方案 | 准时性 | 成本 | 结论 |
|------|--------|------|------|
| 本地 Windows 计划任务 | 高（±秒级） | 需本机开机 | **主通道**（与现有 15:35 任务同机） |
| GitHub Actions cron | 低（UTC 定时普遍延迟数分钟~数十分钟） | 低 | **备份通道**：06:40 UTC 触发 + 程序内等到 14:50；作离线回放/回填用 |
| WorkBuddy 定时任务 | 高 | 已有 | 备用与人工触发 |

> A 股 14:50 = UTC 06:50。Actions 的 cron 不可当作「准点」保障，必须靠程序内等待兜住。

## 6. 存储与复盘底座

| 表 / 文件 | 内容 |
|-----------|------|
| `tail_run` | 每交易日一行：运行时点、全市场样本数、通过初筛数、候选数 |
| `tail_pick` | 候选明细：快照字段 + 分项得分 + 总分 + 所属组 + 是否组内最优 |
| 事后回填列 | 当日收盘价 / 次日开盘·收盘 / 后续 N 日涨幅（复用现有 `perf` 口径） |

落地顺序：**先落本地 JSON（与现有 `data/` 一致）→ 口径稳定后再同步 D1**，避免早期反复改表结构。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 14:50 快照字段缺失（换手需估算） | 误筛 | 关键字段缺失一律「不通过」并记录 `data_gap` |
| 分时接口只给最新交易日 | 历史不可回放 | 快照强制落库 + `--offline` 用落库数据重算 |
| GitHub cron 延迟 | 错过 10 分钟窗口 | 本地任务为主；Actions 内 sleep 到点 |
| 无历史样本，无法回测 | 规则全靠经验 | 先小样本观察，强制落库，2–4 周后做首轮复盘再调阈值 |
| 阈值对某日行情过拟合 | 噪音多 | 阈值全配置化；每日记录「候选 → 实际结果」命中率 |
| 报告公网发布泄露交易意图 | 隐私 | 默认只存本地；需上线时用 Pages + 随机路径或不发布 |
