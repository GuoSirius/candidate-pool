# 定时任务与调度口径

> **一句话**：交易日有 **3 个定时任务**（尾盘观察 / 尾盘正式 / 次日初筛），每个都跑在**两条通道**上
> ——本地 WorkBuddy 计划任务 + GitHub Actions。本文是这两条通道的唯一对照表。

## 1. 双通道拓扑

| 任务 | 本地（WorkBuddy） | GitHub Actions | **实际取数时点** | 本地推送 | Actions 推送 |
|------|-------------------|----------------|------------------|----------|--------------|
| 尾盘·**观察** | 14:30 | `tail-observe.yml`（`20 6 * * 1-5` = 14:20 触发） | **14:30** | ✅ 微信/邮件 | ❌ 静默（`--no-notify`） |
| 尾盘·**正式** | 14:50 | `tail-screen.yml`（`40 6 * * 1-5` = 14:40 触发） | **14:50** | ✅ 微信/邮件 | ✅ 微信/邮件 |
| 次日**候选池** | 16:00 | `daily-screen.yml`（`30 7 * * 1-5` = 15:30） | **15:30** | ✅ 微信/邮件 | ✅ 微信/邮件 |

- **GitHub cron 只负责「触发」**，普遍延迟 1–5 分钟，所以尾盘两条工作流都把 cron 提前 10 分钟，
  再在 Runner 内**等到真正的口径时点**。见下节。
- **谁推送**：两侧都跑会产生重复通知。若要消重，给本地那两个任务加 `--no-notify`，保留 Actions 推送
  （或反之）。**观察口径默认只有本机推**，`tail-observe.yml` 静默。
- **本地 16:00 那次**不在 Actions 的 15:30 之后独立取数，而是复用同一份收盘数据；
  15:30 跑初筛是安全的——`lastClosedTradingDay()` 的判据是「`hour < 15` 才算未收盘」，
  15:30 已过界，锚定日仍是**当日**。

## 2. 尾盘为什么必须「等窗口」

`tail.config.js` 里有一道**有意的时段守卫**：

| 参数 | 值 | 作用 |
|------|-----|------|
| `session.observeFrom` | `'14:30'` | 14:30 之前的启动被判定为「未到尾盘观察时点」，**静默跳过** |
| `session.cutFrom` | `'14:50'` | 正式口径的起点；收盘后 120 分钟内仍可补跑 |

不加参数直接跑，14:30 之前**一律拒绝**（提示改用 `--intraday`）。这道门是**刻意保留**的：
否则定时任务上午空跑，还会推送一条「0 候选」的假通知。

因此 `tail-observe.yml` 里那段 **`Wait for observe window`** 不是冗余步骤——它在 Runner 内
等到 14:30 整再启动脚本。**删掉它，14:20 启动会被守卫静默跳过，当天观察口径就没有产物。**

> Runner 时钟是 UTC。14:30 北京时间 = **06:30 UTC**，写等待逻辑时别按本地时区算。

## 3. 尾盘三种口径（`--intraday` 是唯一的「随时可跑」入口）

| 口径 | 何时生效 | 段区间 | 存档文件 | 写 D1 | 通知 |
|------|----------|--------|----------|-------|------|
| `cut`（正式） | ≥14:50 自动；收盘后 120 分钟内可补跑 | 固定 **14:30 → 14:50** | `eod-<日>.json` | ✅ | ✅ |
| `observe`（观察） | 14:30–14:50 自动 | **14:30 → 当前时点** | `eod-<日>-obs.json` | ✅ | 本机推 / Actions 静默 |
| `intraday`（盘中） | **仅显式 `--intraday`**，09:30 起任意时点 | **滚动**：往前 `segMinutes`（默认 20）**个已成交分钟** | `eod-<日>-intraday.json` | ❌ 强制 `--no-d1` | ❌ 强制 `--no-notify` |

三条要点：

1. **存档文件名默认「一天一个」**，不带时点 —— 观察与盘中的「尾盘段」都是**相对窗口**，不同时刻的结果
   本来就不该横向比较，逐个留档没有复盘价值。要完整保留某一次，显式加 `--stamp`
   （观察 → `-obs<HHMM>`；盘中 → `-intraday<HHMM>-w<窗口>`）。
   多次运行的痕迹看存档里的 `runs[]`，时点看 `doc.cutAt`。
2. **盘中模式强制不写 D1、不推送**：D1 只接受 `formal` / `observe` 两种口径，混入近似值会污染复盘对比。
3. **盘中不要改 `segMinutes`**：段涨幅门槛（`tailSegMinPct = 0.5%`、满分 2.0%）是按 **20 分钟**标定的。
   实测同一份快照 20 分钟 → 40 只、30 分钟 → 87 只，段涨幅中位数 1.05% → 0.93%，
   即**只是放宽度**。跨窗口必须同步重新标定权重。

> ⚠️ **段区间起点必须按「已成交分钟」回数**（`eod/lib/trading.js::backTradedMinutes`）。
> 用墙钟减法在下午刚开盘时会把起点落进**午休**，起点 K 线不存在 → `tailMetrics` 返回 `null`
> → 13:00–13:19 会**静默 0 候选**。分时标签是**起始分钟**（0930…1130 → 1300…1500），
> 「起点正好落在 13:00」是合法的；全天 242 根 = 240 成交分钟 + 收盘快照。

## 4. 落库目标（本机默认双写）

`eod/lib/store_d1.js::targetArgv()` 决定写哪个库：

| 场景 | 远程 D1 | 本地 `db/local.db` |
|------|---------|--------------------|
| **本机跑（默认）** | 写 | 写 |
| **GitHub Actions（默认）** | 写 | 不写 |
| 显式 `--local` | 不写 | 写 |
| 显式 `--both` | 写 | 写 |

- 判别依据是 **`GITHUB_ACTIONS` 环境变量**：CI 里没有有意义的 `db/local.db`（每次都是全新容器），
  所以只写远程；本机跑一次就把本地库补齐，复盘 / 离线查询才用得上。
- 本机的 `gen_candidates.js` 链路（`db/write_live.js`）早已固定 `--both`，尾盘这条现在与之对齐。

## 5. 排查：三种「看着跑了其实没跑」

| 现象 | 根因 | 处理 |
|------|------|------|
| 报告生成了，但 D1 / 网页查不到 | 尾盘工作流缺 `CF_ACCOUNT_ID` / `CF_D1_DATABASE_ID` / `CF_API_TOKEN`，落库步骤**静默跳过** | 补 Secrets；**必须显式传**这三个变量，工作流不会自动带上 |
| Actions 到点没跑 / 跑在「昨天」 | GitHub cron 只按 default 分支**最新提交**上的 schedule 求值，且普遍延迟 1–5 分钟 | 用 `workflow_dispatch` 手动验证一次；新工作流提交当天不要指望立刻生效 |
| 观察口径 0 候选、无产物 | 14:30 之前启动，被 `session.observeFrom` 守卫静默跳过 | 确认工作流里的「Wait for observe window」还在 |
| 13:00–13:19 盘中模式 0 候选 | 段区间起点落进了午休 | 确认用的是 `backTradedMinutes`（已修，勿退回墙钟减法） |
| 微信/邮件收到两条一样的 | 本地与 Actions 两侧都推了 | 给一侧加 `--no-notify` |

## 6. 常用命令

```bash
npm run tail:selftest        # 尾盘自检（含时段守卫 / 盘中放行 / 跨午休起点 / 文件名规则）
npm run selftest             # 一把跑 paths + scaffold + tail + db
node eod/tail_screener.js --paths        # 看落点，不做任何实质动作
node eod/tail_screener.js --intraday --stamp   # 盘中手动跑一次并按时点留档
node eod/tail_screener.js --replay eod/data/eod-<日>[-口径].json --no-notify   # 存档重算（--no-notify 必带）
```

> `--replay` 刷新存量报告时**必须带 `--no-notify`**，否则会真的推微信/邮件。
